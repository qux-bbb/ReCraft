# M1 进展 — 分析核心

> 状态：进行中（2026-10-23 起）。第一项交付：**函数发现 v1 + 评测基线**。

## 1. 本轮交付

| 内容 | 说明 |
|---|---|
| `recraft-analysis` | 函数发现：种子（`.pdata` / 导出 / 入口 / TLS）+ 递归下降；`.pdata` 提供精确边界，非 `.pdata` 函数走基本块直到 ret/尾调用 |
| `corpus/` | 无 CRT 的 MSVC 评测语料（14 个导出函数，覆盖分支/循环/switch/递归/间接调用/浮点/位运算），导出表 + `.pdata` 即 ground truth |
| `recraft eval` | 对任意 PE 计算 recall / precision / `.pdata` 边界准确率 / 指令数 / 耗时 |
| `recraft analyze` | 分析并把结果写入项目（`func.flags & 1` 标记为派生数据，用户自定义函数不会被覆盖） |
| 字符串提取 | ASCII + UTF-16LE，按 256 KiB 分块扫描可读段，跨块 run 续接；结果落 `string` 表 |
| xref 建链 | 直接 call / 分支 / 数据引用（绝对或 RIP 相对寻址）落 `xref` 表；`recraft xrefs --addr` 查询 |
| 导入命名 | 加载时 IAT 槽位命名为 `MODULE.dll!Api`；`analyze` 给匿名函数写 `sub_<hex>`；反汇编自动标注指令目标 |
| API 分类 | 有序子串规则归类（network/file/registry/process/thread/crypto/service/anti-analysis/ui/memory/other），落 `api_tag` 表；`recraft imports` 查看 |
| UI | 顶部 Analyze（F5）；侧栏 5 个面板：段/函数/字符串/导入/引用，均可点击跳转；反汇编显示 `sub_...` 与导入名标注 |

## 2. 实测基线

| 样本 | ground truth | detected | recall | precision | `.pdata` 边界 | 指令 | 耗时 |
|---|---:|---:|---:|---:|---:|---:|---:|
| `corpus.exe`（无 CRT） | 19 | 19 | **1.000** | **1.000** | 7/7 | 272 | 1.9 ms |
| `notepad.exe` | 386 | 443 | **1.000** | 0.871 | 386/386 | 13,141 | 7.9 ms |
| `kernel32.dll` | 2460 | 2575 | **1.000** | 0.955 | 1532/1532 | 78,391 | 158 ms |

指标解读：

- **recall 的含义**：ground truth 里的函数起点有多少被找到。kernel32 的 1697 个导出里有 211 个是转发导出/非代码导出，无法分析，已在评测中排除并单独计数。
- **precision 是下界**：`notepad.exe` 没有导出，ground truth 只有 `.pdata`；分析额外找到的 57 个 call target 很可能是真实函数（CRT 内部辅助函数），但没有独立来源验证，所以按"未匹配"计数。
- `.pdata` 边界 100% 是构造性的：种子来自 `.pdata` 时直接沿用其 end，这验证了数据结构但没有独立验证边界算法；非 `.pdata` 函数的 end 目前是"最远指令末尾"，还需要更细的边界启发式。

## 3. 字符串与 xref（第二批）

`recraft analyze` 现在同时产出字符串表与 xref 表（均为派生数据，可重复生成）：

| 样本 | 字符串 | call 边 | 分支边 | 数据引用 | 总耗时 |
|---|---:|---:|---:|---:|---:|
| `corpus.exe` | 39 | 1 | 26 | 8 | 8.6 ms |
| `notepad.exe` | 3,578 | 618 | 1,533 | 1,348 | 34.6 ms |

- 字符串扫描覆盖所有可读段（含 PE 头/DOS stub，因此 corpus 的 39 条里有相当一部分是节名和 stub 文本，这是预期行为）。
- corpus 里 `corpus_banner` 的 `lea rax, [rip+…]` 被识别为到字符串 `0x140002000` 的 data xref，`recraft xrefs --addr 0x140002000` 可反查；这正是"从代码跟到字符串"的最小闭环。
- UTF-16 提取处理了 ASCII 字符串尾部 + NUL 被误判成宽字符的问题（例如 `"…corpus\0"` 之后紧跟 `L"ReCraft…"`），并支持跨 256 KiB 块的中断续接。
- call 边偏少是因为 `/O2` 把多数调用内联了，不是漏检。

## 4. 导入命名与 API 分类（第三批）

- **IAT 槽位命名**：加载时把每个导入写成 `MODULE.dll!Api`（按序号导入写成 `MODULE.dll!#413`），因此反汇编里 `jmp qword ptr [0x140029910]` 会直接显示 `; COMCTL32.dll!#413`。
- **函数自动命名**：`analyze` 给没有现成名字的函数写 `sub_<hex>`（`name.kind = 2`，派生数据）；加载器名/用户改名优先（`INSERT OR IGNORE`，重新分析不会覆盖用户命名）。
- **API 分类规则**：`recraft-analysis::categorize` 用有序子串规则把导入归入 network / file / registry / process / thread / crypto / service / anti-analysis / ui / memory / other，规则表很小、可解释，属于启发式。
- **api_tag**：分析时把"引用 IAT 的指令地址 → 限定 API 名 + 类别"写入 `api_tag` 表，用来回答"这个函数调了哪些敏感 API"。

`notepad.exe` 实测（同一项目内）：

| 项 | 数量 |
|---|---:|
| 导入 API | 340 |
| api tags | 422 |
| 自动函数名 | 442 |
| 分类 | anti-analysis 4 / crypto 2 / file 7 / memory 12 / network 3 / process 6 / registry 19 / thread 5 / ui 8 / other 274 |

`other` 占比高是因为规则表只覆盖常见敏感面；后续按需扩充，不影响排序/过滤使用。

## 5. UI 面板（第四批）

侧栏从 2 个 tab 扩到 5 个，全部读派生表、可点击跳转：

| tab | 内容 |
|---|---|
| Segments | 段列表 |
| Functions | 分析出的函数区间（点击跳到函数入口） |
| Strings | 字符串列表 + 实时子串过滤（最多渲染 2000 条），点击跳到字符串地址 |
| Imports | `module!api [category] ×引用数`，点击跳到首个调用点（无引用则跳到 IAT 槽） |
| Xrefs | 当前选中行的引用来源，按 call/jump/data 标注，点击跳到引用指令 |

- 反汇编列表面板现在会显示 `sub_...`、`IAT 名` 标注（来自上一批的命名），选中行变化时自动刷新 Xrefs。
- UI 无窗口 smoke test 扩展为 `headless_side_panels_render`：用真实 notepad 项目跑 analyze + 字符串持久化，然后依次渲染 5 个 tab，断言数据与布局都正常。这是当前唯一可自动化的 UI 回归手段（远程会话截图读回仍不可靠）。

## 6. 算法要点

1. 种子优先级：`.pdata`（精确 start/end）> 入口 > 导出 > TLS > call target。
2. 每个函数按基本块遍历（visited 集防环），收集直接 call 边；离开函数范围的直接跳转视为尾调用/回调，作为新函数种子。
3. 只接受落在可执行段内的起点；拒绝落在已知函数体内的起点（防止把跳转表/回调中间地址当函数）。
4. 上限：单函数 20k 指令、全局 5M 指令，防病态样本。

## 7. 复现

```powershell
powershell -File corpus/build.ps1                 # 需要 MSVC
cargo run -p recraft-cli -- eval corpus/build/x64/corpus.exe
cargo run -p recraft-cli -- eval C:\Windows\System32\kernel32.dll
cargo run -p recraft-cli -- analyze project.rcraft
cargo run -p recraft-cli -- funcs project.rcraft
cargo run -p recraft-cli -- strings project.rcraft
cargo run -p recraft-cli -- xrefs project.rcraft --addr entry
```

CI 会在 `cargo test` 之前构建语料，`recraft-analysis` 的集成测试直接断言 recall/precision > 0.95、`.pdata` 边界完全一致、字符串可提取且存在到 banner 的 data xref。

## 8. 下一步（按优先级）

1. **控制流图**：函数级 CFG 视图（egui 自绘，节点/边虚拟化）。
2. **函数边界增强**：非 `.pdata` 函数的 padding/对齐/`int3` 终止启发式；跳表识别（switch 表）。
3. **运行时恢复**：Go `pclntab`、Rust demangle。
4. **性能**：1 GiB 样本的全量分析、后台任务与取消。

风险：xref 目前只覆盖被函数发现扫到的代码，未覆盖的代码（未被引用的函数）没有 xref；precision 下界缺少独立 ground truth（可考虑 PDB 解析或符号服务器）；跳表识别与异常处理（SEH/C++ EH）是下一批硬骨头。
