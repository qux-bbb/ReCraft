# 2026-11-05 进展：局部变量重建（消除伪代码中的寄存器名）

本轮的起点是"反编译结果仍然通篇是 `eax`/`r8d`/`xmm0`"。根因不是文本层没折叠干净，而是
**发射器只有寄存器视图、没有局部变量**：L2 的每条语句都直接写机器寄存器名。这一轮新增
`recraft-decompile/src/variables.rs`，在全部文本 pass 之后把寄存器值流重建为 C 局部变量。

## 1. 效果（notepad 502 个函数，全量 L2）

## 2. 算法

### 2.1 结构化路径（`recover_structured`）

1. **解析**发射器已经排好版的 C：`if`/`else if`/`while`/`do`/`switch`/`case`、`break`/
   `continue`、`goto`/`loc_` 标签、`return`、内联 `if (…) break;`。不认识的形状（`for`、
   结构损坏、无对应标签的 `goto`）整函数回退，不猜。
2. **建语句级 CFG**：条件是一个只读节点；`if` 两条出边、循环回边、`switch` 到各 `case`、
   `goto` 到标签、`break`/`continue` 走最近的循环/switch 上下文。
3. **可达定义 + 并查集**：给每个寄存器写一个定义 id；前向数据流在每个节点保留
   "当前值"的变量 id，汇合点把不同 id 并成一个变量（等价于无 phi 的 SSA coalescing）。
   循环因此自然得到一个循环变量。按基本块活跃性（liveness）剪枝，死定义不会把变量拖长。
   汇合点先分类再合并：全命名或全 raw 才 union；命名与 raw 混合时不 union，而是在汇合点
   新建一个 raw 值（读到这里保持寄存器名），让汇合前的普通赋值仍能命名（`dee443b`，
   这一条把 notepad 的寄存器行从 2 079 降到 1 292）。
4. **调用**：`call` 定义为 `rax` 的新值。若返回值在活跃出口被读，语句改写成
   `v4 = GetLastError();`；否则保持裸调用。`return eax;` 会变成 `return v4;`。
5. **宽度**：每个变量取"定义宽度与所有读取宽度的最大值"。64 位变量被 32 位读时打印
   `(uint32)v`；x64 的 32 位写按零扩展处理；`al = 0` 这类 8/16 位写是读改写：
   `v2 = (v1 & 0xffffffffffffff00) | (uint8)(0);`。
6. **有符号**：只在 `/* signed */` 上下文出现过的变量声明为 `int32`/`int64`；混用无符号
   上下文时声明为无符号，并在有符号读处显式 `(int32)v`，不改变比较语义。
7. **`__asm`**：未建模指令的寄存器效果按小表恢复（`mov`/`cmpxchg`/`xchg`/`rdtsc`/`cpuid`/
   `imul`/`div`/`rep stos`/`cmov*` 等）。只有这些指令**写出的值**保持寄存器名（raw 局部），
   正常赋值会立刻把它变回命名变量；未知指令按"clobber 全部 GPR"处理。这样 `__asm` 字符串
   里的寄存器与紧随其后的机器状态仍然一致，而不是假装旧 C 变量还是对的。

### 2.2 直线回退（`recover_linear`）

有些函数发射器会输出非法 C（已知形状：`while (1) { … } else { … }`，即 then 臂以循环结尾时
少一个 `}`；另有 `continue`/`break` 落在循环外）。这类函数的结构化解析必然失败，回退到
**只在同一个直线段内改名**：

- 遇到 `if`/`while`/`do`/`switch`/`case`/标签/`goto`/`return`/`break`/`continue`/`__asm`
  就清空环境；因此没有任何值跨分支、跨循环或跨标签被改名，语义是精确的（宁可不改，不改错）。
- 直线段内的寄存器写仍按宽度/部分写/调用返回处理；`while` 条件不参与改名（循环回边上的值
  可能来自上一次迭代）。
- 变量名按类型池复用：一段结束就把名字还池，下一段可复用，所以声明数量取决于"同时活跃的
  值"而不是整个函数。notepad 的 9 868 行巨型函数只产生 221 个声明。

## 3. 发射器非法 C 的两个修复（本轮附带发现）

变量重建把两个此前被"看起来像结构"掩盖的 bug 暴露出来；修完后巨型函数才进入结构化路径。

### 3.1 后向 goto 折叠跨出 if 分支（`5d8f694`）

`fold_backward_gotos_into_loops` 原来按**行**统计花括号净变化：`} else {` 的净值是 0，
于是把「label 在 then 臂、latch 在 else 臂」的区间也当成了循环体，生成

```c
do { … } else { … } while (1);
```

`normalize_infinite_loops` 再把它变成 `while (1) { … } else { … }`。这不是合法 C，变量
重建只能整函数回退。改为按字符阅读顺序计数：深度一旦低于 label 所在层就拒绝折叠
（跳过字符串字面量）。代价是 2 个函数保留 `loc_` + `goto`：结构化 487 → 486、
`goto` 450 → 387（错误折叠本来会引入更多 goto）、标签 265 → 268；收益是
`sub_140013154` 变成可解析的 13 197 行（含 371 个 goto），变量重建覆盖其中 13 086 行，
只剩 222 行 `__asm` 相关的 scoped raw。

### 3.2 复合赋值写错变量（`0b3cc59`）

结构化的值流给每个寄存器写都新建变量，包括 `rdi -= rbx;` 这种读改写：LHS 的读解析到
旧变量，写却落到新变量，渲染成 `v8 -= v3;`（v8 从未赋值）。现在复合赋值把结果写回它
读到的变量（`v4 -= v3;`），宽度按定义参与类型推断但不影响符号性；没有可读旧值的不可达
节点保持寄存器形状。新增两个回归测试（直线复合、`eax += 1` 后按 64 位读的强制转换）。

### 3.3 循环外的 `break`/`continue`（`258d641`）

两类问题都会生成非法 C：

1. `emit_loop` 的 `while (1)` 路径与 `emit_do_while` 在关闭 `}` 之后才输出循环体内
   未发射的剩余块，此时 `loop_stack` 里还留着该循环，于是这些块里跳回循环头/出口的边
   被打印成 `continue`/`break`，而它们已经在循环外。
2. `fold_return_tail_labels` 与 `fold_last_label_tails` 会把以 `return` 结尾的 tail
   复制到另一个 `goto` 处；若 tail 内部含 `break`/`continue`，复制点的循环上下文与
   原来不同（或根本没有循环）。

修法：先 `pop` `loop_stack` 再输出剩余块（跳转变回 `loc_` 标签 + `goto`）；复制 tail
前拒绝含 `break`/`continue` 的 tail。notepad 的 `sub_140004f4c`、`sub_14000647c` 与
crackme 的 `sub_140007594` 三份快照随之变成合法标签跳转。用脚本扫描全部 L2：
`while … else` 0 处、循环外的 `break`/`continue` 0 处（`switch` 内的 `break` 合法）。

### 3.4 单操作数 `imul` 提升为 C（`recraft-ir`）

`imul r/m32` 原来整条留在 `__asm` 里，因为它写 `edx:eax` 两个寄存器。32 位有符号乘积
在 `int64` 里不会溢出，因此可以精确展开为：

```c
edx = (uint32)((((int64)((int32)(eax)) * (int64)((int32)(src))) >> 0x20));
eax = (uint32)((int64)((int32)(eax)) * (int64)((int32)(src)));
```

（先写 `edx`，此时 `eax` 还是旧值；低半写回 `eax`。两处 `int32` 强转是必要的：寄存器
在伪代码里的 C 类型是无符号的，直接 `(int64)` 会把负数零扩展。）死代码分析会在低半确实
未被读取时删掉 `eax` 赋值。64 位 `imul` 需要 128 位中间值，仍保留为 `__asm`。

效果：notepad 的 `__asm` 134 → 113，含寄存器名的行 1 292 → 1 187，`sub_140013154`
的 raw 行 222 → 111；`sub_1400206b4` 中一条被后续覆盖的 `var_e0 = xmm0;` 也随之被死写
分析删掉（已确认无读者）。notepad 两份 L1 快照更新为上述展开。

## 4. 已知边界

- **剩余 1 187 行含寄存器名**：其中 111 行在 `sub_140013154`，来自其余 `__asm` 的
  scoped raw（`lock xadd`/`cmpxchg` 的隐式累加器、`cpuid`、`rdtsc` 等）。其余主要是
  47 个含 `__asm` 的函数，以及 `sub_140012f3c`（18 行）/`sub_140011af8`（7 行）这类
  **未结构化**函数的入口寄存器读（`rdi`/`rsi`/`ebx` 在入口没有定义，直线回退保守地保留
  寄存器名，不伪造未初始化的局部变量）。
- `sub_140013154` 现在是合法 C，但仍是 1620 块 / 371 处 goto 的未结构化函数；变量重建
  走 CFG，所以 13 086 行已经变量化。
- `__asm` 字符串内部仍是寄存器拼写（它就是汇编文本），不计入 §1 的"函数体"行；与 asm
  直接相连的读（`v = rax;`）也保持寄存器名，因为改名会让读者误以为它是普通局部变量。
- 直线回退里跨控制行的值保持寄存器名，所以回退函数的命名率明显低于结构化函数；这是保守
  换正确性的取舍。
- 变量声明与合法 goto 会抬高 L2 行数（29 442 → 39 054），这是"像 C 源码 + 合法 C"的必要
  成本；`metrics` 的 goto/结构化指标反而更好（goto 450 → 388）。

## 6. golden 与 L2 变量的关系

`golden_text`/`write_golden` 使用的是 **L1**（`pseudocode_l1`），变量重建只在
`info.is_some()`（L2）时运行。这是有意的：L1 是快照的稳定基线，L2 是给人读的源码视图。
本轮有 7 份 L1 快照变化（notepad 6 + crackme 1），不是变量化造成的，而是 §3 的结构修复
把非法 C 还原成合法 C、以及 §3.4 的 `imul` 提升；其余 778 份不变。L2 侧由 lint、15 个
单测与导出抽查保护。
