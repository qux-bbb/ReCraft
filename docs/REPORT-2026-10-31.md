## 3. 这一阶段做了什么（按主题）

**命名（最大收益）**

- 指针实参的字段访问 `argN->field_XX`：类型推断为 `void*` 时，若某偏移只有一种访问宽度，
  也写成 `arg1->field_10`（266 → 777 处）；同偏移出现两种宽度则保留强制转换。
- 全局数据按地址与宽度命名：`*(u64*)(0x140036648)` → `qword_140036648`（1 725 处，189 个函数），
  计算地址保留原样。
- 地址常量按指向命名：数据段 → `off_<addr>`，函数入口 → 函数名（回调指针），
  命中字符串字面量 → 字符串（511 → 337 处裸地址）。
- 栈上参数：x64 无 push 的常量序言下，`frame+0x28` 起的只读槽是调用方参数，
  写成 `arg5`/`arg6`…并补全签名；x86 全部栈参数按槽宽取 `int32`，并按"载入值是否被当作
  基址"推断 `char*`/`wchar_t*`/`int32*`。
- 结构/句柄：RECT/POINT/MSG 字段、`hKey`/`hwnd`/`hIcon` 等句柄槽、结构实例名。

**结构**

- 常量比较折叠：`eax = 0x111; if (arg2 > eax)` → `if (arg2 > 0x111)`（35 个函数）。
- 实参溢出槽折回实参（72/88 处），`nested_loops(int32 arg1, int32 arg1)` 这类重名参数修正。
- 跳表分支的标签补全（crackme 180 处 `goto` 曾引用未定义标签，已修）。
- 跳到函数入口的标签不再落在函数头之外（Go 样本借此多恢复 24 个函数）。

**性能**

- 文本 pass 里的三处平方级扫描改为一次索引/预计算：槽引用索引、标签索引、逐行大括号计数
  （800 ms → 225 ms），输出逐字节不变。
- `RECRAFT_PROFILE=1 recraft decompile …` 打印各阶段耗时。

**护栏**

- `recraft lint [--level l1|l2] [--limit N] [--json]`：六条输出不变量自检，违规非零退出。
- `recraft metrics`：新增 `labels`、`inline asm statements` 计数。
- golden 快照：corpus x64（31）、corpus86（32）、go（40）。

## 4. 仍然存在的限制

1. **多入口循环**：notepad 15 个、Go 196 个函数保留 `goto`，共同原因是一处向后跳转落在
   `if` 分支内部（重试/清理入口），循环有两个入口点；规则式 CFG 化简无法表达，需要把
   第二入口提升为守卫条件（结构器工作，不是文本后处理）。
2. `__asm` 剩余 138 行主要是原子指令（`lock xadd`/`lock cmpxchg`/`xchg`）、
   1 操作数 `imul`/`mul`、间接 `jmp`、未建模标志的分支。
3. 伪 C 里的 Go/C++ 符号名（`go:buildid`、`internal/abi.Name.ReadVarint`）不是合法 C 标识符，
   为便于与符号表对照而保留原样。
4. 结构体/数组类型只做到"字段名 + 访问宽度"，没有真正的类型传播。

## 5. 复现命令

```bash
cargo build -p recraft-cli

# 质量指标（覆盖率 / 结构化率 / 标签 / inline asm）
target/debug/recraft.exe metrics <project>

# 输出不变量自检（六条规则，违规非零退出）
target/debug/recraft.exe lint <project> --level l1 --json

# 逐函数文本快照
target/debug/recraft.exe golden <project> --dir tests/golden/corpus --check
target/debug/recraft.exe golden <project86> --dir tests/golden/corpus86 --check
target/debug/recraft.exe golden <go-project> --dir tests/golden/go --limit 60 --check

# 单函数反编译（L0 / L1 / L2）
target/debug/recraft.exe decompile <project> --addr 0x14000e950 --l2

# 各阶段耗时
RECRAFT_PROFILE=1 target/debug/recraft.exe decompile <project> --addr <addr> --l2
```

**改动文本 pass 时的自检顺序**：先看 `lint`（结构是否仍合法）→ 再看 golden diff（形状是否按预期变化）
→ 最后看 `metrics`（结构化率/覆盖率是否提升）。只有三层都解释得通才提交。

**已知剩余工作**（见 §4 与 `docs/QUALITY.md`「结构化失败的形状」）：多入口循环（不可规约流图）的
守卫提升 / 节点复制；样本：notepad `sub_140004264`（第 168 个函数，未在快照集内，但其所在工程每次
`recraft lint` 都会检查）、Go `internal/abi.Name.ReadVarint`（已在 `tests/golden/go` 内）。*L2 头部的跳转计数**（`// L2 structure recovery (40 blocks, 2 goto)`）与 `metrics` 的
`goto fallback functions` 交叉核对一致：notepad 15 个函数带头部计数 = metrics 的 15；crackme
40 = 40。因此该头部可以当作"未结构化函数"的清单直接使用。## 6. 验证快照（阶段收尾：c009fb4）

在提交 `05adf0d` 上重跑：五套 golden（notepad 170、crackme 160、corpus 31、corpus86 32、go 60 = **453** 个函数）全部 `mismatched: 0`；`recraft lint` 在 notepad（1004 份文本）、crackme（986）、corpus（62）、corpus86（64）上均 0 findings、exit 0；Go 全量 L1（3261 函数）0 findings。`cargo test --workspace` **141** 个反编译单测全绿。

## 6. 结论

在 notepad/crackme/Go/corpus 四个样本上：

- 输出满足全部六条结构不变量（`lint` 全 0）；
- 三层回归齐全（不变量、快照、指标），任一改动可在一条命令内验证；
- 与阶段起点相比，L2 行数下降约 12.5%，命名类信息（字段/全局/句柄/栈参数）从几乎为零
  增长到数千处，反编译耗时降到 ~1.2 s。

剩余的结构化提升集中在"多入口循环"，需要结构器层面的新规则，已在
`docs/QUALITY.md` 的「结构化失败的形状」中记录具体形状与样本位置。
